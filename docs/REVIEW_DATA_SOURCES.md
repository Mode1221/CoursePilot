# 리뷰 데이터 소스 현실성 점검 (2026-09 기준)

"AI가 신뢰할 리뷰 데이터를 어디서, 합법적으로 가져올 수 있는가"를 실제 약관·판례로 점검.

## 결론 요약
- **네이버 지도/블로그 직접 크롤링 → 사실상 불가(법적 리스크 큼).**
- **네이버 검색 API(블로그/카페) → 2026-09-07 개정으로 "AI 요약/가공" 금지. 기존 8장 RAG 설계는 약관 위반이 됨.**
- **카카오맵 → 사용자 요청으로 제외.**
- **현실적 1순위: Google Places API 리뷰(장소당 5개, 공식·상업적 허용, attribution 필수).**
- 체험단/광고 배제는 100%는 불가하나, 2024 공정위 개정으로 **탐지 신호가 명확해져** 다층 필터로 상당 부분 걸러낼 수 있음.

---

## 1. 크롤링(직접 스크래핑)은 현실적인가 → 위험
- **네이버 vs 다윈중개(2024)**: 공개된 매물정보라도 저작권법상 **DB권 침해** 인정, 다윈에 7,000만원 배상 판결. "공개 데이터=자유 이용"이 아님.
- 형사(정보통신망법)로는 무죄가 난 사례(2022 대법 2021도1533)도 있으나, **민사 DB권·이용약관 위반**은 별개로 계속 인정되는 추세.
- 네이버 지도/플레이스는 이용약관에서 자동 수집을 명시 금지. → **크롤링은 지양(기획서 방침과 동일).**

## 2. 공식 API 비교

| 소스 | 리뷰 제공 | 상업적 이용 | 핵심 제약 |
|---|---|---|---|
| 네이버 지역검색 API | ❌ 리뷰 없음(장소 기본정보만) | ✅ | 좌표/주소/카테고리만 |
| 네이버 블로그/카페 검색 API | △ 텍스트(리뷰 아님) | ✅(일 25,000콜) | **2026-09-07 개정: 원문 가공·요약·재배열 금지, 출처+원본링크 필수** → AI 요약 불가 |
| **Google Places API** | ✅ 장소당 **최대 5개** | ✅(EEA는 2025-07-08 신약관) | 5개 한정, **attribution 필수**, 리뷰 텍스트 장기 캐싱 제한 |
| 카카오맵 | △ | ✅ | 사용자 판단상 신뢰도 낮음 → 제외 |

### ⚠️ 네이버 검색 API 개정(2026-09-07 시행)이 미치는 영향
개정 특약 요지:
1. 검색 API 데이터는 **"네이버 검색결과 제공" 목적으로만** 사용.
2. 받은 데이터를 **독립적으로, 가공 없이 노출** — 앞뒤/중간에 다른 내용 삽입, 순위·내용 수정·요약·변조 **금지**.
3. **원본 출처 표시 + 원본 이동 링크** 제공 의무.

→ 우리 기획서 8장의 "네이버 블로그 텍스트를 수집해 **AI가 요약**"은 이제 **약관 위반**.
합법적으로 쓰려면 "블로그 원문 카드 + 출처/링크를 그대로 노출"하는 형태로만 가능(요약·점수화 불가).

## 3. 권고 아키텍처 (합법 + 신뢰도)
1. **영업정보/좌표/별점**: 지도 API 어댑터(`mapService`) 유지. 리뷰 별점은 Google Places로.
2. **리뷰 텍스트/요약**: **Google Places 리뷰 5개**를 attribution과 함께 사용.
   - 정책 준수: 리뷰 원문 장기 저장 대신 `place_id`만 저장, 표시 시점 실시간 조회 + 출처 표기.
   - 5개로 부족한 RAG 풀은 "요약 근거"보다 "대표 후기 인용"으로 활용.
3. **네이버 블로그 요약 RAG는 철회** → 필요 시 "블로그에서 더 보기" **원문 링크 카드**로 대체(약관 준수).
4. **자체 데이터 축적**: 플랫폼 성장 시 사용자 코스/후기를 1차 데이터로 → 벤더 종속·약관 리스크에서 자유.
5. 보조: 공공데이터(관광공사 TourAPI 등) — 상업적 이용 관대, 리뷰는 없지만 장소 메타 보강.

## 4. 체험단/광고(뒷광고) 배제 방법
2024-12-01 공정위 「추천·보증 심사지침」 개정으로 표기가 강화됨:
- 블로그·카페는 **제목 또는 첫 부분**에 경제적 이해관계 표기 의무.
- "소정의 수수료를 지급받을 수 있음" 같은 **모호·조건부 문구 금지**(명확히 표기해야 함).
- 미래·조건부 대가도 공개 의무.

→ 표기가 **제목/첫문단에 명확히** 오도록 규제되어, 오히려 **탐지 신호가 또렷**해짐.

### 다층 필터(권고)
1. **표기 키워드/패턴**(현재 구현): "협찬·광고·제공받아·원고료·체험단" 등 → **제목/첫문단 가중치 상향**(개정 지침 반영).
2. **구조 신호**: 정형화된 협찬 템플릿, 과도한 이모지/해시태그, 쿠폰·예약링크·업체 연락처 삽입.
3. **계정 패턴**: 특정 업체/카테고리만 반복 게시하는 계정.
4. **정량 신호 우선**: 텍스트보다 별점 분포·방문자 리뷰 수·재방문 언급 같은 정량 지표를 우선(광고에 덜 오염).
5. **LLM 2차 분류**: 1차 통과분을 LLM이 "광고 개연성" 스코어링(보조).
6. **교차 검증**: 여러 출처가 합의하는 장소만 상위 노출(단발 협찬 글의 영향 희석).
7. **소스 선택 자체**: Google 리뷰는 방문자 실사용 비중이 블로그보다 높아 체험단 오염이 상대적으로 적음 → **소스 우선순위 = Google > 블로그**.

### 한계
은닉(미표기) 협찬은 어떤 방법으로도 완전 차단 불가. 현실적 목표: **"명백한 광고 제외 + 정량 지표 우선 + 다출처 합의"**로 신뢰도를 끌어올리는 것.

## 가장 좋은 방법 (장기 권장)
텍스트 리뷰는 소스 불문 광고 오염·약관 리스크가 상존한다. 근본 해결책:
1. **방문 증명 기반 자체 리뷰**: 영수증/위치 인증한 실제 방문자만 후기 작성 → 체험단이
   구조적으로 개입 불가. 전화인증 회원(9장)과 자연스럽게 연결.
2. **정량 신호 우선**: 별점 분포·방문자 수·재방문율은 텍스트보다 조작이 어려움 → 스코어에
   텍스트보다 먼저 반영.
3. **소스 우선순위**: 자체 정량 데이터 > Google 리뷰(합법·attribution) > 네이버(원문 링크만).
콜드스타트는 초기 Google 리뷰로 보완 후, 데이터가 쌓이면 자체로 전환.

## 코드 반영 제안
- `reviews/source.py`: 네이버 블로그 소스는 "요약"이 아니라 "원문 링크 카드"로만 노출하도록 주석/인터페이스 명시. Google Places 리뷰 어댑터를 1순위 소스로 추가.
- `reviews/sponsored.py`: 제목/첫문단 가중, 구조·계정 신호 확장.
- `pipeline/planner.py`: 리뷰 정량 신호(별점 분포·리뷰 수)를 스코어에 반영, 텍스트 의존 최소화.
