# 데이터 수집·활용 전략

기준: **콜드스타트에 강한가**(유저 적어도 쌓이나) · **광고/조작에 강한가**.

## A. 암묵적 행동 신호 (수집 마찰 0, 콜드스타트 최강)
1. 장소 채택 수 — 코스에 포함될 때마다 +1 *(구현)*
2. 북마크 수 — 저장된 코스 등장 +2 *(구현)*
3. **생존율** — AI 추천 후 유지 vs 삭제/교체 → 추천 적중 학습 *(구현: 삭제/교체 시 -1로 상쇄)*
4. 교체로 밀려난 장소 = 음의 신호 *(구현)*
5. 공유/열람 수 — 완성도 대리지표(열람 시 약한 가점) *(구현)*
6. 완주 신호("다녀왔어요") — 실제 방문 시 +3 강한 가점 *(구현)*
7. 재정렬 패턴 — 확정 순서의 카테고리 전이 학습 *(구현)*

## B. 명시적 최소마찰 신호 (원탭, 텍스트 아님 → 광고·약관 무관)
8. 완료 후 👍/👎 — 원탭 만족도(±2 가점) *(구현)*  9. 장소별 ⭐ 빠른 평가 *(구현)*  10. 재방문 의사 토글 — 장소 단위 강한 긍정(+2) *(구현)*

## C. 컨텍스트 신호 (개인화 정밀도)
12. 시간대 컨텍스트 — 장소×데이파트(아침/낮/저녁) 채택 학습 *(구현)*
11. 요청 원문 로그  12. 시간대/요일/동행유형  13. 선언 선호 vs 행동 선호 보정 — 채택 카테고리 학습·개인화 가점 *(구현)*  14. 날씨/계절 *(후보)*

## D. 피드백 루프 (품질 자기개선)
15. Best-of-N 후보 노출→선택으로 목적함수 가중치 학습 — 채택 시드 전략 로깅 *(구현)*
16. 조건 완화 수용률 → 하드/소프트 제약 학습 — 수용률로 완화 강도 조절·키워드 소프트드롭 *(구현)*
17. 코스 점수 vs 실제 만족도 회귀로 계수 튜닝 — 예측점수·만족도 대조 데이터 수집 *(구현)*

## E. 외부 정량 (합법·요약 아님)
18. 별점·리뷰 수(Google, 숫자만) *(구현: 표본 N≥30 만 신뢰)*  19. 공공데이터(TourAPI·LOCALDATA·KOPIS) *(구현)*  20. 실시간 혼잡/영업 *(후보)*

### Google Places SKU (2026-09 정정)
공식 "Place Data Fields (New)" 표 기준으로 **영업시간과 평점은 같은 Enterprise SKU** 다.
예전 문서는 영업시간을 Pro(월 5,000)로 적었는데 사실이 아니었다.

- `businessStatus` 만 Pro 지만, Enterprise 필드와 같은 콜에 얹어도 청구는 가장 비싼
  SKU 로 1회다 → 나눌 이유가 없어 **한 콜로 합쳤다**.
- Text Search(IDs-only, `places.id`)는 별개 SKU 이므로 여기에 다른 필드를 섞지 않는다.
- **월 1,000 콜이 전부**다. 배치 600(하루 20) + 런타임 400 으로 나눠 쓴다.
- 카카오 수집은 **격자 단위**다. 질의당 45건 상한이라 한 점 질의로는 상권당 최대 180건
  (실측 24곳 3,103건). 반경 300m 칸(간격 400m)으로 쪼개 부르면 24곳 340칸, 콜 4,320회
  안쪽(약 25분)에 상권당 수백 곳이 모인다. 카테고리 코드 밖 성격은 보충 키워드로.
- 그래서 수집한 전수(약 15,000곳)를 Google 로 채우는 것은 **무료로는 불가능**하다.
  목표를 **상권별 상위 25곳**(24개 상권 × 25 = 600곳)으로 잡는다. 나머지는
  영업시간 "확인 필요" 표시로 남고, 평점 없이 자체 신호로만 스코어링한다.

### LOCALDATA 파싱 규약
- **원천**: `file.localdata.go.kr` 고정 URL. 업종 단위 **전국** 파일(구원천은 시군구 단위였다).
  브라우저 User-Agent + `Referer: …/file/<slug>/info` 없으면 403.
- **인코딩**: 응답 헤더는 `charset=UTF-8` 이라고 하지만 실제 본문은 **CP949**.
  읽을 때 `cp949`, `errors="replace"` 로 고정한다.
- **주소**: 신원천 헤더에는 `도로명주소`, `지번주소` 가 있다(구원천의 `도로명전체주소`,
  `소재지전체주소` 는 없음). 대조는 도로명 → 지번 순.
- **폐업 판정**(우선순위):
  1. `폐업일자` 가 채워져 있으면 폐업
  2. 아니면 `상세영업상태명` → `영업상태명` 에 `폐업·말소·취소·직권말소·폐쇄·허가취소·휴업`
     중 하나가 들어가면 영업하지 않는 것으로 본다
  정상 영업 값은 `영업/정상`(상세는 `영업`). 휴업도 제외한다 — 당장 갈 수 없는 곳을
  추천하면 안 된다. 실제 값 분포는 `python scripts/localdata_status_dist.py` 로 확인한다.
- **좌표**: `좌표정보(X)/(Y)` 는 중부원점TM(EPSG:5174)으로 보이며 **쓰지 않는다**.
  장소 대조는 상호 + 주소 번지 토큰으로만 한다(좌표계 변환 오차로 엉뚱한 가게를
  지우는 쪽이 더 나쁘다). 좌표를 쓰게 되면 그때 WGS84 변환을 검증한다.
- **적재 범위**: 전국 파일 중 24개 상권의 **(시도, 시군구)** 쌍에 해당하는 행만 인덱싱한다
  (약 2%). 시군구 이름만 보면 부산·대구·인천 중구까지 딸려 온다.
  나머지는 폐업 판정에 쓸 일이 없고, 다 담으면 6GB VM 에서 백엔드가 OOM 으로 죽는다.
- **개방자치단체코드**: 시군구 커버리지·적재 필터 판정에는 **쓰지 않는다**(공식 코드표 대조 전까지
  "미확인"). 대신 주소 문자열에서 시군구 이름을 찾아 24개 상권을 덮는지 확인한다.

### LOCALDATA 업종 슬러그
다운로드 URL 은 `https://file.localdata.go.kr/file/download/<슬러그>/info`,
안내 페이지는 `https://file.localdata.go.kr/file/<슬러그>/info` 다.

| 업종 | 슬러그 | 우리 슬롯 | 상태 |
| --- | --- | --- | --- |
| 일반음식점 | `general_restaurants` | meal, bar | **확인됨**(2026-09, 기본 수집 대상) |
| 휴게음식점 | `rest_cafes` | cafe | **확인됨**(2026-09, 약 208MB) |
| 제과점영업 | 미확인 | cafe | 미확인 — 휴게음식점에 상당수 포함 |
| 단란·유흥주점 | 미확인 | bar | 미확인 — 코스에 넣지 않으므로 우선순위 낮음 |
| 관광·문화(공연장·박물관 등) | 미확인 | activity | 미확인 — TourAPI·KOPIS 로 대체 중 |
| 체육시설·노래연습장 | 미확인 | activity | 미확인 |

- **확인됨**= 실제 요청으로 200 text/csv 를 받은 것. 나머지는 슬러그 이름을 확인하지
  못해 **미확인**으로 둔다(추측한 슬러그를 코드에 박지 않는다).
- 슬러그를 확인하면 `LOCALDATA_CSV_URLS` 에 추가만 하면 된다 — 수집·파싱 코드는 그대로다.
- meal/cafe/bar 는 위 두 파일로 덮인다. activity 는 LOCALDATA 폐업 판정 대상이 아니다.

### 하지 않는 것
- 네이버플레이스·카카오맵 크롤링(약관·판례 리스크)
- LLM 웹검색으로 영업시간 1차 확인(부정확·느림·비쌈 → 최후 폴백 + "확인 필요" 표시만)
- 리뷰 원문을 품질 스코어에 사용

### 저장·갱신
- 영구: place_id·좌표·카테고리·자체 신호 / TTL: Google 영업시간 30일·평점 90일
- 폐업·업력 주 1회(전체), 영업시간 30일(최근 90일 내 추천된 활성 집합), 평점 90일(인기 상위)
- 배치: `scripts/build_places.py`(구축) / `scripts/refresh_places.py`(갱신)
- 무료 한도 소진 시 호출 자체를 차단(`app/quota.py`), `/admin/metrics` 에 사용량 노출

## 활용(정밀화)
- 시간 감쇠(최신 트렌드), 지역×카테고리 정규화(상대 인기)
- 개인화 벡터(pgvector) *(후보)*, 협업 필터링 — 장소 공동 채택 co-occurrence *(구현)*, 콜드스타트 폴백 체인 — 행동 신호 전무 시 외부 평점 의존 *(구현)*
- 목적함수 계수 A/B 학습

## 구현 순서
1. 생존율/교체 신호 *(본 변경)* — 기존 편집 이벤트에서 공짜 수집
2. 피드백 루프(완화 수용·후보 선택 로깅)
3. 원탭 평가(👍/⭐)
4. 컨텍스트(동행유형) + 시간감쇠·지역정규화
